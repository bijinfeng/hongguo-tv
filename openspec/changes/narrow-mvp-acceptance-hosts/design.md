# Design

## Context

See `proposal.md` — Why. 当前验收规则分散在三层：ENGINEERING §9 定义「功能验收以正式入口中的真实数据和实际使用流程为主」，§5 要求 arm64 真机验收，§8 的 CI 矩阵既有 macOS／Windows／Linux 桌面行也有 TV 行；VALIDATION 与台账按这些规则逐条记「物理电视待验」「Windows／Linux 未验」；活跃 OpenSpec 的退出条件又各自复述一份宿主清单。

结果是同一个事实（物理电视缺失）在十余处被重复计为阻塞，而真正的产品失败（TV 真实播放首帧失败、账号进度上传未通过）反而被环境项淹没。

## Goals / Non-Goals

**Goals:**

- 一个事实一个来源：验收宿主矩阵只在 ENGINEERING §9 定义，其他文档链接它。
- 保持既有证据不丢失：物理设备与 Windows／Linux 的未验事实、原因与证据索引原样保留，只改变它们的地位（平台限制 ≠ MVP 阻塞）。
- 让模拟器结果可被计为 TV 验收通过：DPAD、媒体键、系统 IME 在 AVD 上是可注入、可重复的输入，不因设备形态降级。
- 不改变任何视觉、功能或契约条款。

**Non-Goals:**

- 不删除物理设备验收工作，不删除 Windows／Linux 构建目标。
- 不把已在模拟器上通过的项追溯改成「已验收」——它们仍需正式入口的真实数据流程；本次只去掉「非物理设备」这一层阻塞。
- 不调整发布流水线；Windows／Linux 仍出未签名预览。
- 不重跑产品门禁：本次是纯文档变更。

## Decisions

### 验收宿主矩阵放在 ENGINEERING §9

ENGINEERING 已经是「工具、协作、安全和验收标准」的唯一来源，验收层级的定义在 §9。把矩阵放这里，VALIDATION、台账、路线与各活跃变更都链接 `#验收宿主矩阵`，不再各自维护宿主清单。

### 模拟器结果在 TV 端等值于真机结果

TV 的验收关心的是「遥控器能不能完成浏览、输入、播放与返回」，这在 AVD 上可以完整注入：DPAD、媒体键、硬件 Escape、系统 Gboard 与 TalkBack 都在模拟器上有真实系统组件。物理电视额外增加的是硬解、4K 输出、真实 overscan 与观看距离——这些是**环境特性**，不是交互语义。因此把它们单列为平台限制，交互验收保留在模拟器。

### 平台限制保留事实，不保留阻塞

VALIDATION 的每条物理设备或 Windows／Linux 未验项都保留原文事实与原因，只在结论句上区分「不阻塞 MVP」。这样既不删失败，也不把外部环境缺失读成产品缺陷。

### 不追溯改写历史

`docs/history/**` 与 `VALIDATION` 的证据索引表保留当时的判断与措辞。历史记录不是当前指令，改写它会破坏证据的可追溯性。

## Risks / Trade-offs

- **风险**：把物理电视降级可能被读成「不用管 TV 真机」。缓解：ENGINEERING §9 明确「不能用模拟器结果宣称为物理设备通过」，平台限制条目仍逐条列出。
- **风险**：Windows／Linux 构建失败可能被当成可忽略。缓解：§8 明确两平台失败仍按构建兼容问题处理，只是不计入 MVP 功能验收。
- **权衡**：TV 硬解与长播在物理设备上的真实问题会留到发布之后才暴露。这是用户明确接受的范围收窄，已在 VALIDATION 保留原因。

## Migration Plan

1. ENGINEERING §9 新增矩阵，§5／§8／§10 对齐。
2. PRODUCT、DESIGN、ARCHITECTURE、TV_DEVELOPMENT 与 9 份功能／组件文档就地改写。
3. VALIDATION 增加口径说明与平台限制段，逐条结论加注；台账与路线同步。
4. 三份主规范与活跃变更 task 措辞对齐。
5. 跑 OpenSpec strict 与文档链接检查。

## Open Questions

无。宿主范围由用户确认；Windows／Linux 是否属 MVP 与物理电视项如何记，均已在此决定。
