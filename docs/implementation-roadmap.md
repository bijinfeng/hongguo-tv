# MVP 实施路线

更新：2026-11-15。本文件只维护当前开发顺序、批次边界与交接规则，不追加逐次运行日志。旧路线及实施过程保存在[历史快照](history/implementation-roadmap-2026-11-15.md)。

## 范围与事实来源

首期仍完整对齐 [PRODUCT.md](../PRODUCT.md) 确认的功能，覆盖 Web、桌面（macOS／Windows／Linux）与 Android TV 的适用能力。分批交付不缩减 MVP，不把搜索／播放／历史的局部闭环当成最终产品。

评论、回复、弹幕、剧评、点赞及其入口／设置按用户决定排除；收藏、追更、预约继续保留。离线下载、TV 系统频道及附属资产先核对固定上游和实际能力，不造协议、任务队列、指标或成功状态；未确认不等于永久不支持。

## 当前起点

内容发现、详情／系列、Rust 播放及原生装配已有大量实现，但不少项目只有合成边界或部分真实流程证据，不能统一标记完成。账号迁移、同步、收藏／追更／预约、统计及维护／跨平台交付仍有明确缺口，逐项状态以台账为准。

游客历史管理 E1 尚未整体验收。当前播放器状态修正已有在途工程检查；真实 Web 流程曾在后段详情超时，Desktop native 曾返回 `409 / PLAYBACK_IDENTITY_MISMATCH`，封面加载、完整焦点／后台、当前 TV 包等还有未通过或未验项。主会话正在收尾修复及原生日志诊断，后续诊断结果记在 VALIDATION，不在本路线重复维护即时结果。

此前真实 Web／TV 成功证据保留其源码、平台和范围；新失败也保留。安全依赖、物理电视、Windows／Linux、公开 Web 隔离、正式签名升级等开放项不能被工程通过或旧包验收覆盖。

## 开发队列

保留原 A–G 批次含义，以便台账、证据和既有变更继续对应：A 基础 UI，B 播放，C 原生独立运行，D 内容发现与系列，E 账号／记录，F 维护与附属能力，G 全量验收与交付。后续按下面的依赖推进，避免在单一焦点或历史切片无限加项。

第 4 项从现在持续补验，最终集中核对，不等全部功能写完才首次使用真实数据。安全／CI 及平台工具链阻塞也提前暴露；物理设备缺失保持未验，不悄悄删减范围。

### 并行边界

主会话负责集成、契约边界和当前队列；有可独立交付的任务时再分配实施者。可并行账号核心、既定契约下的界面、独立设置／许可能力或真实验收；不要把全部并行额度用于重复调查和重复审查。

每个任务写明负责路径、输入契约、交付物、受影响平台与退出条件。DTO／状态所有者先由一个负责人定稿；共享入口、台账和验证记录由集成者汇总。不得并行覆盖同一文件，或在契约未定时各造一套实现。

共享 Cargo／NSH 输出、图形宿主、模拟器、账号会话及全量验证由一个执行者串行使用；其他人继续独立编码或只读审查。复用已确认缓存，临时目录只存缓存／可再生产物，交付源码留在主工作区。

## 每批怎样执行

1. **固定交付边界。** 在相关 OpenSpec 中用一小段明确用户流程、平台、范围外事项、接口／状态所有者、定向命令、真实验收和 UI 审查条件。复用已有变更，不为每个小修复新建一套文档。给本批工作量预估；遇到新阻塞时更新预估和队列，不虚报 MVP 完成时间。
2. **先接真实能力，再扩展界面。** 核对上游和真实响应，尽早从正式入口走通代表流程；产品实现与必要边界回归同步推进，不先铺大量假页面和合成状态再找真实数据。
3. **开发中运行定向检查。** 按改动层运行 Rust／状态／控件／宿主回归。NSH 界面改动必须 check 和 build；DTO 改动执行 codegen 与 codegen:check；依赖变化执行 security。使用已有命令，只有缺少可重复验证入口时才补最小工具，不为一次运行建设通用框架。
4. **冻结本批代码再做完整门禁。** 集成完成并审查后，由一人运行一次完整 `pnpm verify`；正在编辑的文件不作为本批稳定输入。新发现修复后先做定向验证，再按影响决定重跑范围；本批交付源码必须有适用的完整门禁依据。不能一边持续改产品一边反复启动全量检查。
5. **真实流程和 UI 双审。** 正式入口使用当前真实服务／实际播放形成的数据，完成本批流程；界面在实际宿主观察还原度、完整度和输入／返回行为。独立审查覆盖功能与界面，依据证据给结论；headless、核心 probe、截图或合成宿主不能互相代替。
6. **交付并进入下一批。** 汇总变更、真实流程／合成边界／工程检查的各自结果、未解决项和下一步。按既有授权作聚焦本地提交，保留不相关改动；不因局部通过关闭整个变更或 MVP，不擅自推送、归档或发布。

真实验收涉及账号写入、短信或外部副作用时遵守已有明确授权；缺授权只阻塞相应步骤，不虚构成功或让其余独立开发全部停住。

### 失败与证据复用

- 将长流程拆为可独立复现的用户任务，记录各段结果和失败点；后段失败不抹掉已证明的局部事实，也不能把整条链记为通过。重启／同步／跨模块连续性仍需最终端到端验收。
- 证据关联源码身份（含相关未提交文件）、入口／包、数据来源、平台、时间及步骤。源码与依赖范围未变的证据可以复用；DTO、共享状态、控件、宿主、配置或上游语义变化后检查受影响消费者，不把过期证据算到新版本。
- 失败先分类为产品、上游／数据、环境或验收工具问题。有新假设／修复／环境变化才针对性复验；不在相同条件下整套反复重跑取绿灯。网络重试遵循真实产品行为并保留原始失败。
- 单一故障持续无新信息时，交接明确错误、最小复现、已排除因素、下一步和负责模块；继续无依赖的队列。不得通过放宽身份校验、安全门禁、等待断言或改用合成数据关闭故障。
- 状态区分“待核对／待实现／已实现待真实验收／已验收／平台不适用”；另记工程检查和阻塞原因。任务勾选数、测试数量和 OpenSpec 格式通过不表示功能完成率。

## 文档收敛与 OpenSpec 生命周期

当前路线代替旧文中的“按日期追加进度”和“VALIDATION 只追加”作为后续整理方式；历史结果和失败证据仍须保留。每类事实只在对应文件维护，其他地方链接，不同时改写多份长篇运行叙事。

| 文档层         | 保留内容                                         | 更新方式                                                                         |
| -------------- | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| 当前规则       | 产品、架构、工程、设计与长期能力 spec            | 直接维护有效条款；重要决策附原因或链接归档，不混入每日操作日志                   |
| 当前计划与状态 | 本路线、功能台账、活跃变更 tasks                 | 路线维护顺序，台账维护实现／缺口，tasks 维护本变更待办；不按每次工具调用追加进度 |
| 当前验收       | VALIDATION                                       | 目标为当前验收矩阵、开放失败与证据索引；新结果指向历史运行证据，不隐藏旧失败     |
| 历史与产物     | docs/history、OpenSpec archive、忽略的 artifacts | 历史开头注明非当前指令及权威入口；凭据、缓存和运行配置不入库                     |

安排一次独立文档收敛批次，由集成者在当前产品切片交付后协调执行，不与产品线程同时改根文档：

1. 对照功能台账和真实验收标准复核现有 complete 变更，逐项区分规范成立、实现完成和真实验收；不能把 21 个历史 complete 直接视为均可验收或自动批量归档。
2. 按目录／发现、播放、记录、账号、原生会话等实际能力补主规范；核对重叠 delta 的最终规则，再按项目 OpenSpec 流程同步、校验，符合完成条件后归档。没有证据的任务保持开放，部分完成不强制归档。
3. README 收敛为入口／命令／状态链接，VALIDATION 收敛为当前矩阵＋开放问题＋证据索引，根规则中的旧执行历史迁入 history 并修复链接；保留重要决策，不大删全部 Markdown。
4. 用格式、相对链接和 OpenSpec 校验验收文档整理，不因纯文档调整重跑产品构建；不把这次整理扩大为重写全部资料，也不阻塞独立产品开发。

本轮仅重写路线并保存历史快照；上述主规范、归档和根文档整理尚未执行，不宣称已经完成。

### 重复、分布与上下文成本复核

2026-11-15 本轮盘点：Git 跟踪 Markdown 241 份；按忽略规则搜索到 249 份（含本地新增及技能资料），其中 `openspec/changes` 108 份、`docs/design` 顶层 25 份。与此前约 522 份的统计口径不同，不据数量差异宣称已删减。文档数量本身不等于上下文用量；实际读取的正文才产生直接成本。

当前 AGENTS 指定先读的自身及五份根文档合计约 20.4 万字符，VALIDATION 占约 69%，是优先收敛对象。组件设计／演进／覆盖审查中，RankingCard 同一段 306 字符的说明在三处重复；大量相近规则虽非逐字相同，也形成多处维护成本。ARCHITECTURE 仍有“原生 bridge 未迁移”的旧阶段描述，与已有实现及同文后续记录并存；旧设计 brief 仍有评论上下文，不能作为当前产品要求。

## 主会话继续入口

先读取本路线、台账相关行、VALIDATION 当前相关失败及 E1／播放变更任务，复用在途检查和诊断结果，收尾当前修复。随后按账号／会话与隔离边界启动下一独立批次，并按资源与路径边界并行推进可交付模块。E1、真实原生播放及其他未验项继续有负责人和后续步骤，不以“继续账号”替代解决。

每次交接只报告：**本批交付、真实验收结果、工程检查、阻塞及下一批**。无需重新阅读全部历史或重新证明未受影响的基础链路；完整 MVP 最终仍按全部范围验收。
